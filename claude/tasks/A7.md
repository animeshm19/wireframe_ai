## What changed

One logical change, in five files.

`src/lib/design-jobs.ts` — 182 lines to 47. `createDesignJob`,
`updateDesignJob`, `subscribeDesignJob`, `deleteChatFromBackend`, `jobFileUrl`,
`refineJobSpec` and the `DesignJob` type are gone. Only `uploadJobAttachment`
remains, unchanged, including its `user-uploads/{uid}/…` path — that path and
the rules that go with it are A2's.

`src/components/wireframe/chat-types.ts` — new `ChatDesign` carried on the
message: `id`, `prompt`, `spec?`, `source?`, `model?`, `interpretation?`.
`designJobId` kept only as a deprecated field the loader migrates away.

`chat-shell.tsx` — `send()` posts the assistant message immediately with
`design: { id, prompt }`, then calls `extractRingSpec(text)` directly and
patches `spec`/`source`/`model`/`interpretation` onto that message when it
returns. `studioJobId` became `studioDesignId`, and the Studio is handed
`studioDesign?.spec` rather than an id. `reallyDelete` no longer touches
Firestore. `loadPersisted` runs a `migrate()` that turns a pre-A7
`designJobId` into a `design` whose prompt is the preceding user message.

`design-job-card.tsx` — takes `design: ChatDesign` instead of `jobId`. No
subscription, no `job` state, no `subscribeError`. `failed` is now purely the
kernel's error; there is no server status that can fail it.

`studio-workspace.tsx` — `StudioWorkspace({ spec?, onClose })`. The job→spec
`useEffect` and its `subscribeDesignJob` call are replaced by an effect keyed
on the *value* of the incoming spec, so a spec that lands while the Studio is
already open is picked up, and a chat re-render does not discard edits made in
the Studio.

The two dev harnesses (`src/studio-only.tsx`, `src/studio-wrapped-test.tsx`)
were updated to the new props. **Both are gitignored**, so they are not in the
diff — they exist only on this Mac.

### Why (a) and not (b)

B1 replaces this collection with `designs` + a `versions` subcollection, and
its own prompt says it must not build on a shape A7 is removing. (b) would
have created a second persistent record — `designJobs`-as-design-record — for
B1 to migrate and then delete.

The stronger reason is what the collection was doing. `createDesignJob` wrote
the document, then called `extractRingSpec` **from the browser** and wrote the
result back; `DesignJobCard` and `StudioWorkspace` read that result via
`onSnapshot`. Firestore was a message bus between two React components in the
same tab, with a server round trip in the middle. Both components already
build geometry with the OCCT kernel in the browser and already fall back to
`withDefaults(parseSpecFromPrompt(prompt))`. So (a) removes a round trip, not
a feature.

Three consequences, all in B1's favour:

- Chat sessions already live in `localStorage` under `wireframe-chat-v1`, which
  is what B1 migrates. The spec and the interpretation now sit on the message,
  so B1 finds a complete design record in the one place it already reads,
  instead of joining localStorage to Firestore by id.
- `status` / `progress` / `outputs` only ever meant something to the worker.
  With no document there is no state machine, so "no document left in a state
  nothing will ever advance" is structural rather than swept.
- One unmetered `addDoc` per chat message is gone — a surface A5 and B2 both
  care about.

What (b) would have bought — a design surviving a browser-data wipe — is not
available today either: the document is only reachable through a message id
that lives in localStorage. B1 delivers that durability properly.

### The Studio symptom — it does not reproduce, and the old explanation was wrong

**The claim was: Studio mounts with `spec: null`, so the generate effect never
fires and the viewport stays empty. Every clause of that is false in the
current code.**

`studio-workspace.tsx:41` initialises `useState<RingSpec>(DEFAULT_SPEC)` — not
null. The geometry effect at `:150-155` is

```ts
const specKey = JSON.stringify(live);
useEffect(() => {
  const t = setTimeout(() => generate(live), 120);
  return () => clearTimeout(t);
}, [specKey, generate]);
```

— no guard, no early return, no dependency on a job. It fires 120ms after
mount whatever the subscription does. And the subscription itself already
defaulted: `withDefaults(job.spec ?? parseSpecFromPrompt(job.prompt))`. There
was no code path in which the Studio waited on a server.

Run against the app, before any change on this branch, in the browser:

| Case | How | Result |
|---|---|---|
| No spec at all (`jobId=""`, subscription skipped) | `studio-only.html` | **full platinum solitaire, framed and lit** |
| Non-empty jobId, StrictMode, AnimatePresence, chat-shell's exact wrapper | `studio-wrapped-test.html` | **full ring** |

The second case's console shows the subscription failing outright —

```
[error] Firestore Subscribe Error: {code: permission-denied, … Missing or insufficient permissions.}
```

— which is the strongest available version of "the spec never arrives", and the
ring renders anyway.

**What the symptom actually was.** The live collection says it plainly. Of the
eleven queued documents, **ten have `spec: null` and exactly one has a spec**
— `YfNVh5391JwQnrJbTg4Q`, the newest. The cause is `refineJobSpec`:

```js

if (result.source !== "ai") return;      // <- writes nothing
```

`extractRingSpec` falls back to the local parser on any failure — which is
A6's open item 5, `extractRingSpec` timing out at up to 116s against a 60s
function — and on that path `refineJobSpec` returned without writing. So the
document usually stayed at `spec: null` forever. A6 read the one document that
had a spec and concluded the board was wrong; the board had read the older
ones and concluded specs were always null. **Both observations were correct
about different documents, and neither was the cause of an empty viewport.**

My reading of the history: the empty scene was real before commit `62f146d`
("Rebuild the chat and the Studio as tools, not screens") and `b26df53`
("production build fix" — the worker code-splitting failure, now held by
`vite.config.ts`'s `worker: { format: "es" }`), which moved generation into
the browser and gave both components a defaulted spec. The symptom was fixed
there; the explanation was never retired, and it survived into the board and
into this task. The untracked file `src/studio-wrapped-test.tsx` on this Mac
still carries the comment *"Delete once the Studio bug is fixed"* — a harness
built to chase a bug that had already gone.
