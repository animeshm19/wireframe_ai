## What changed

### `a5ec7d4` — keep the ranked model chain, not just its head

`pickModel` already computed six models that pass the policy, logged them as
`considered`, and threw five away. That list is a failover chain we were
already paying for.

`pickModelChain(ai, logger, role)` is new; `pickModel` is now exactly
`chain[0]` and its behaviour is unchanged. The per-role cache holds the whole
ranking and **hands every caller a `.slice()`**. That copy is the structural
guarantee for acceptance item 3: nothing downstream can reorder or truncate
what is cached, so a request that fails over to `gemini-3.7-flash` leaves
`gemini-3.8-flash` first choice on the next call. Failover is per request and
can never become a permanent demotion.

A **pinned** role gets a chain of exactly one. A pin is a deliberate human
decision about which model runs; failing over off it would quietly undo that.

### `53ae4f3` — retry once, then fail over down the chain

New module `functions/resilient-extract.js`. `extractWithFailover` takes the
chain and an injected `generate`, `parse`, `now`, `sleep`, `random`, and
returns a result object rather than throwing — so the caller decides what a
failure means to a customer, and nothing depends on mutating an SDK error
that may be frozen.

| | |
|---|---|
| Retry | first choice gets 1 retry after a **250–500ms jittered** backoff |
| Failover | then one attempt each down the ranked chain, first success wins |
| Retryable | 429, 502, 503, 504; status names `UNAVAILABLE`, `RESOURCE_EXHAUSTED`; network-level (`ECONNRESET`, `fetch failed`, …); our own attempt timeout |
| Never retried | 400, 401, 403, 404, 422, and any schema violation — ours, and retrying hides them |
| Per attempt | 12s cap, enforced by a race whose abandoned promise is pre-caught |
| Whole budget | 45s, measured from the **start of the request**, checked before every attempt |
| Discovery | separately bounded at 10s. 45 + 10 < 60 |

`index.js` now logs the model that **actually answered**, `firstChoice`,
`failedOver`, `attempts` and a readable `attemptChain`
(`gemini-3.8-flash#1 503, gemini-3.8-flash#2 503, gemini-3.7-flash#1 ok`), and
returns the answering model to the client. Before this it returned the model
we asked first, so a spec produced by 3.6 travelled to the card labelled 3.8.

**The metric.** Every terminal path of the model layer emits exactly one line
carrying `metric: "spec_extraction_outcome"`, with `outcome` of `model` or
`parser_fallback` and a `reason` (`ok`, `exhausted`, `fatal`, `budget`,
`discovery`). `fatal` counts as a fallback because that is what the customer
gets; `reason` is what separates our bug from Google's queue.

Be precise about the denominator, because a metric nobody can state the
denominator of is how the last set of numbers went wrong. **It counts
authenticated requests carrying a 1–2000 character prompt that reached the
model layer.** It excludes the argument-validation throws (rejected requests,
not extraction attempts) and it cannot see a client that never reached the
function at all — offline, CORS, not deployed — which also ends on the parser.
So it is a **floor** on the customer-visible parser rate. It is also exactly
the denominator the pre-A8 baseline below was counted over, which is what
makes before and after comparable.

### `3d5afa7` — say when the regex parser produced the design

The card had a line for this **and it was unreachable.** "The model did not
answer" is gated on `!design.spec`, and the parser always supplies a spec, so
the moment the fallback resolved the note disappeared and the customer saw a
finished card with a green tick and no hint at all. A7-close's "at best a soft
hint in the UI" was generous: on the real path there was none.

A parser result now says so, in amber, beside the issues warning. It says
**"the design model did not answer"** and deliberately not "every model was
busy": `source: "parser"` is set on *any* client-side failure, and the browser
cannot tell which. Naming a cause we do not know would be a new false
statement in place of the old one.

### `4bc13df` — four holes an adversarial verifier found

Reported by a subagent given only the diff. All four were real.

1. **A fatal error was being retried.** `statusOf` preferred `.status` merely
   because it was *defined*, so `{ status: "UNAVAILABLE", code: 400 }`
   returned null, fell through to text matching, and a 400 of ours was walked
   down all six models — the exact bug-hiding the module exists to prevent.
   It now takes whichever field is numeric.
2. **502 and 504 were treated as fatal.** A Google frontend under load returns
   502, 503 and 504 for the same condition. Two of the three were reported to
   the customer as *"Could not interpret that description"* and logged as our
   bug. Retryable now. 500 INTERNAL still is not — it is the genuinely
   ambiguous one. An unclassified numeric status (a gRPC `14`) now falls
   through to the status **name** instead of being guessed from a number.
3. **Discovery sat outside the budget.** `startedAt` was taken on entry to
   `extractWithFailover`, *after* an unbounded `await ai.models.list()`. The
   real worst case was discovery + 45s with nothing stopping it crossing the
   60s function timeout. Budget now runs from the start of the request;
   discovery is bounded at 10s.
4. **The card asserted a cause it cannot know** (fixed as described above).

Plus: the failure log advertised `chain.slice(0, 8)` while the walk stops at
`MAX_MODELS = 6`; an empty chain now logs as a discovery failure instead of
escaping as an unlabelled `INTERNAL` with no metric; and the metric comment
now states its real denominator instead of "all".

The verifier also flagged `GEMINI_MODEL_EXTRACT` leaking out of the pinned-role
test. **That one is wrong** — `model-picker.test.js:85` already has
`test.afterEach(cleanEnv)`. Recorded so nobody re-fixes it.

### The five required proofs, all no-network, no real clock

`functions/resilient-extract.test.js` injects `generate`, `parse`, `now`,
`sleep` and `random`, so "3.1 seconds per refusal" is something the test
*states* rather than waits for.

| Acceptance criterion | Test |
|---|---|
| one 503 then success on retry | `one 503 then success on the retry — same model, no failover` — asserts 2 attempts, both to 3.8, exactly one backoff, 250 ≤ backoff < 500 |
| two 503s then success on the second model | `two 503s then the second model answers` — calls are `[3.8, 3.8, 3.7]`, still exactly one sleep (a failover is not a backoff) |
| every model failing → parser result flagged as such | `every model refuses: no spec, marked exhausted, every model tried once` — 7 attempts, `ok:false`, `spec === undefined`, all six models in order |
| a 400 NOT retried | `a 400 is NOT retried and does NOT fail over` — 1 attempt, outcome `fatal` |
| cache still returns 3.8 first after a failover | `after a failover, the NEXT call still gets 3.8 first` — destroys the returned chain (`shift`, `shift`, `reverse`, `length = 1`) then re-asks; still 6 long and still 3.8 first |

Also proved: a 400 whose message contains "UNAVAILABLE" is still fatal; 401,
403, 404 fatal; a schema violation fatal after 1 attempt and no failover; 500
INTERNAL not retried; 502/504 and gRPC-shaped errors retried; a network
`ECONNRESET` retried; the caller's chain is never mutated; an attempt that
never answers is abandoned and its late rejection does not crash the instance;
no attempt is started that cannot finish before the deadline; and 25s of
discovery leaves room for exactly one attempt, with the whole request still
landing inside 45s.

## Unsure about / open

1. **Is 12s the right per-attempt cap?** The only clean success in the window
   took 7034ms, and a pre-fix one took 87086ms before being killed. 12s
   comfortably covers the former and cuts the latter, but the sample is two
   requests. Guess: fine, and 15s would also be fine. Cost to run down: one
   `gcloud logging read` over `durationMs` once a real sample exists — a week
   of traffic, not a command.
2. **Should 500 INTERNAL be retryable?** Deliberately excluded, on the brief's
   reasoning. If the after-measurement shows a residue of `reason: "fatal"`
   with `errorStatus: 500`, that judgement is wrong and one line changes it.
   Cost: one log query after the deploy.
3. **The parser rate this metric can see is a floor.** It cannot count a
   client that never reached the function. Closing that needs a client-side
   beacon, which is a new decision, not a fix. Guess: the gap is small, since
   the function is reachable whenever the app loads. Cost: unknown until B1
   gives us somewhere to write it.
4. **`test:brep` was not run to completion** (item 4 in *Owed*). Guess: green,
   since A8 touches no kernel file and 12/24 passed clean. Cost: four minutes
   on the Mac.
5. **The chain is capped at `MAX_MODELS = 6`,** which is the whole list today.
   If discovery ever returns more, the 7th onwards is never tried. Deliberate
   (the budget has to be bounded by something), but it is a number, not a law.
6. **A pinned role cannot fail over.** Correct, in my reading — a pin is a
   human decision — but it means `GEMINI_MODEL_EXTRACT` turns A8 off for that
   role. Worth knowing before anyone pins one in an incident.
